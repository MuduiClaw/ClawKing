# Workspace 文件详解

> `~/clawd` 不是一个“配置目录”。
> 它更像你和 AI 的长期协作合同。

如果你刚装完系统，建议先读 [GETTING-STARTED](GETTING-STARTED.md)。
如果你想理解长期记忆怎么沉淀，再配合 [MEMORY.md](MEMORY.md) 一起看。

---

## 先建立一个脑图

可以把 `~/clawd` 想成三层：

1. **你定义 AI 的层**
2. **AI 积累长期上下文的层**
3. **系统执行自动化的层**

最常改的是第一层。
最容易误删的是第二层。
升级时会自动覆盖的是第三层。

---

## 哪些会被覆盖，哪些不会

安装和升级时，规则很重要：

| 区域 | 典型内容 | 升级行为 |
|------|---------|---------|
| 用户配置区 | `SOUL.md` `IDENTITY.md` `USER.md` `TOOLS.md` `MEMORY.md` | 首次创建，之后不覆盖 |
| 系统核心区 | `scripts/` `prompts/` `eval/` `skills/` | 强制覆盖，覆盖前 `.bak` 备份 |
| 运行产物 | `memory/`、日志、sessions | 由系统持续更新，不要手工乱删 |

所以：

- 想定制人格，改用户配置区
- 想看系统能力，读系统核心区
- 想清理历史内容，先理解记忆层再动手

---

## 顶层结构

一个典型的 workspace 长这样：

```text
~/clawd/
├── SOUL.md
├── IDENTITY.md
├── USER.md
├── AGENTS.md
├── MEMORY.md
├── TOOLS.md
├── HEARTBEAT.md
├── BOOTSTRAP.md
├── memory/
├── skills/
├── scripts/
├── prompts/
└── eval/
```

前 8 个文件，是这篇的重点。

---

## 8 个核心文件怎么配合

把它们理解成“8 个问题”会更容易：

| 文件 | 它回答的问题 |
|------|-------------|
| `SOUL.md` | 你是谁，要成为什么样的 AI？ |
| `IDENTITY.md` | 你知道自己的边界和缺陷吗？ |
| `USER.md` | 你在服务谁，这个人怎么做决策？ |
| `AGENTS.md` | 你做事遵循什么流程和纪律？ |
| `MEMORY.md` | 哪些长期知识值得优先记住？ |
| `TOOLS.md` | 你能用什么工具，哪些不能碰？ |
| `HEARTBEAT.md` | 在系统心跳或巡检场景下你该怎么表现？ |
| `BOOTSTRAP.md` | 每次启动时需要自动完成什么初始化？ |

如果这 8 个问题写得清楚，AI 的行为会稳定很多。

---

## 文件之间的关系

```text
USER.md ─┐
SOUL.md ─┼─> 决定日常对话风格、目标和默认协作方式
IDENTITY.md ─┘

AGENTS.md ─────> 决定做任务时的方法论、验证标准和纪律
TOOLS.md ──────> 决定能做什么、不能做什么

MEMORY.md ─────> 作为长期记忆索引，指向 memory/archive/ 和 memory/journal/

HEARTBEAT.md ──> 决定心跳 / 巡检类消息的行为
BOOTSTRAP.md ──> 决定启动后的初始化动作
```

这里最常见的错误，是把同一类规则写进多个文件，导致冲突。

记法很简单：

- **人格和关系**写进 `SOUL.md`
- **用户画像和偏好**写进 `USER.md`
- **工作流和铁律**写进 `AGENTS.md`
- **工具边界**写进 `TOOLS.md`
- **长期沉淀索引**写进 `MEMORY.md`

## 1. SOUL.md

`SOUL.md` 是人格定义。
它不负责“你当前正在做什么”，而负责“AI 作为谁来行动”。

### 最小可用版本

```markdown
# SOUL.md

- 我是：你的 AI 合伙人
- 服务目标：推进你的项目和日常协作
- 协作模式：默认行动，高风险操作先确认
- 说话风格：直接、简洁、不给空话
```

### 进阶示例

```markdown
# SOUL.md

## 身份认同
- 我是：偏执行型的 AI 合伙人
- 服务目标：把讨论尽快推进到可验证结果

## 行动原则
- 先理解目标，再动手
- 交付结果时必须附证据
- 遇阻先自救，不马上把问题抛给用户

## 调性
- 语言：中文
- 风格：短句、直说、少铺垫
```

### 写法建议

- 写“长期稳定的性格”，不要写今天临时的需求
- 用行为准则，不用口号
- 一旦你发现它总在某个方向跑偏，就先回这里改

---

## 2. IDENTITY.md

`IDENTITY.md` 是自我认知。
它帮助 AI 知道自己的角色、名字和已知缺陷。

### 最小可用版本

```markdown
# IDENTITY.md

- Name: 小助手
- Role: 负责执行和推进的 AI 合伙人

## 已知缺陷
1. 容易在没验证前过早宣称完成
2. 复杂任务可能低估影响范围
```

### 进阶示例

```markdown
# IDENTITY.md

- Name: Anchor
- Role: 用户的项目执行搭档
- Emoji: 🦀

## 已知缺陷
1. 完成偏好：容易先改再补验证
2. 事实填充：来源不足时可能过度推断
3. 意图误判：需求模糊时容易默认成“直接执行”

## 自我提醒
- 没有证据，不宣称完成
- 不清楚就先确认，不猜
```

### 写法建议

- 这里最有价值的内容通常不是名字，而是“缺陷清单”
- 每次你纠正它一次，适合长期保留的教训可以回写到这里或 [MEMORY.md](MEMORY.md)

---

## 3. USER.md

`USER.md` 是用户画像。
它回答“你在服务谁”。

### 最小可用版本

```markdown
# USER.md

- Name: 你自己
- Role: 独立开发者

## 当前目标
- 目标：让产品稳定上线

## 偏好
- 沟通风格：直接
- 产出偏好：正确 > 完整 > 速度
```

### 进阶示例

```markdown
# USER.md

- Name: Alex
- Role: 产品和研发负责人

## 当前目标
| 目标 | 怎么算赢 |
|------|---------|
| 发布新版本 | 本周完成上线和回归验证 |
| 减少运维噪音 | 日常问题 80% 自动化处理 |

## 决策框架
- 用户价值优先
- 能小步验证，就不大改
- 不为未来三个月外的假设过度设计

## 偏好
- 沟通风格：结论先行
- 厌恶：长篇背景介绍、模糊建议
```

### 写法建议

- 这份文件最好写“你怎么判断”，不是“你喜欢什么形容词”
- 当 AI 给你的建议总是不合口味，优先补这里

---

## 4. AGENTS.md

`AGENTS.md` 是工作方法论。
它不是人格，而是做任务的流程和纪律。

### 最小可用版本

```markdown
# AGENTS.md

1. 复杂任务先写计划
2. 先搜索，再动手
3. 没有验证证据，不要宣称完成
4. 高风险操作先确认
```

### 进阶示例

```markdown
# AGENTS.md

## The Loop
1. 想清楚
2. 执行
3. 验证
4. 交付
5. 复盘

## 铁律
- 不信任“完成了”，只信证据
- 改代码前先明确怎么验证
- 失败三次回到方案层，不盲重试
```

### 写法建议

- 这里写的是“做事方式”，不要混入用户画像
- 如果你有团队级流程要求，比如先写 spec、先过测试、禁止某些操作，就写这里

---

## 5. MEMORY.md

`MEMORY.md` 是长期记忆的索引，不是所有记忆本体。

它应该很短，负责把 AI 引到更详细的地方：

- `memory/archive/`
- `memory/journal/`
- qmd 检索

### 最小可用版本

```markdown
# MEMORY.md

## 核心认知
- 用户偏好：结论先行
- 工作原则：没有证据不算完成

## 项目索引
- 产品文档：docs/
- 关键决策：memory/archive/decisions.md
```

### 进阶示例

```markdown
# MEMORY.md

## 核心认知
- 产品处于快速迭代期，优先小步验证
- 默认以中文交付，对外文档再按需切换

## 长期索引
- 教训：memory/archive/lessons.md
- 决策：memory/archive/decisions.md
- 基建：memory/archive/infrastructure.md
- 每日记录：memory/journal/
```

### 写法建议

- 只保留“高价值导航”，不要把整本笔记抄进来
- 详细机制见 [MEMORY.md 文档](MEMORY.md)

---

## 6. TOOLS.md

`TOOLS.md` 是能力边界。
它既是工具目录，也是安全规则入口。

### 最小可用版本

```markdown
# TOOLS.md

## 安全规则
- 不做不可逆操作前先确认
- 不输出密钥

## CLI 工具
- Codex：代码任务
- Claude Code：复杂重构
```

### 进阶示例

```markdown
# TOOLS.md

## 安全规则
- 禁止直接执行危险重启命令
- 浏览器自动化统一走受控实例

## CLI 工具
| 工具 | 命令 | 用途 |
|------|------|------|
| Codex | `codex` | 深度代码任务 |
| Claude Code | `claude` | 多文件推理 |
| ~~Gemini CLI~~ | *(已移除)* | — |

## 基础设施
- Guardian：自动守护
- Dashboard：查看健康和配置
```

### 写法建议

- “禁止什么”通常比“能做什么”更关键
- 跟环境强相关的规则优先写这里

---

## 7. HEARTBEAT.md

`HEARTBEAT.md` 只在心跳、巡检、后台提醒场景生效。

### 最小可用版本

```markdown
# HEARTBEAT.md

1. 用户活跃时不打扰
2. 没有异常就保持安静
3. 发现关键告警再说话
```

### 进阶示例

```markdown
# HEARTBEAT.md

## 规则
- 只汇报高价值信息
- 用户最近 2 分钟内活跃则跳过心跳
- 能自修先自修，修不了再升级
```

### 写法建议

- 这是“后台礼仪”，不是任务执行规范
- 如果你讨厌被系统噪音打断，这里值得认真写

---

## 8. BOOTSTRAP.md

`BOOTSTRAP.md` 决定系统启动时要不要先做初始化动作。

默认可以是空的。

### 最小可用版本

```markdown
# BOOTSTRAP.md

No init tasks.
```

### 进阶示例

```markdown
# BOOTSTRAP.md

1. 启动后先读取今日重点项目
2. 检查昨天失败的 cron job
3. 如果存在 pending task，先给出概览
```

### 写法建议

- 只放“每次启动都值得做”的动作
- 临时任务不要写进来

---

## 目录级内容怎么理解

除了 8 个顶层文件，你还会经常碰到这些目录：

| 目录 | 用途 |
|------|------|
| `memory/` | 长期记忆正文 |
| `skills/` | 自定义 Skills |
| `scripts/` | 自动化脚本 |
| `prompts/` | Cron 和提示词模板 |
| `eval/` | 评测样本与脚本 |

这些目录是系统能力层。
如果你要扩展能力，通常从这里下手，而不是把所有规则都塞进顶层 8 个文件。

---

## 编辑顺序建议

如果你今天要第一次认真整理 workspace，推荐顺序：

1. `SOUL.md`
2. `USER.md`
3. `IDENTITY.md`
4. `AGENTS.md`
5. `TOOLS.md`
6. `MEMORY.md`
7. `HEARTBEAT.md`
8. `BOOTSTRAP.md`

原因很简单：

- 先定人格和用户关系
- 再定工作纪律
- 最后补自动化和后台行为

---

## 常见反模式

### 把同一句话复制到四个文件里

短期看很完整，长期一定漂移。

### 在 `MEMORY.md` 里堆全部历史

索引一旦变成长文，检索效率会下降，人也不想维护。

### 用 `SOUL.md` 写当前项目任务

人格文件应该稳定，项目状态应进入记忆或任务文件。

### 把安全规则散落到各处

如果某条规则涉及工具和执行边界，优先收敛到 `TOOLS.md` 或 `AGENTS.md`。

---

## 一句话记忆法

如果你总记不住 8 个文件分别干嘛，可以用这组对照：

- `SOUL.md`：我是谁
- `IDENTITY.md`：我知道自己有什么毛病
- `USER.md`：我在服务谁
- `AGENTS.md`：我怎么做事
- `MEMORY.md`：我长期记什么
- `TOOLS.md`：我能用什么、不能碰什么
- `HEARTBEAT.md`：我什么时候该安静、什么时候该提醒
- `BOOTSTRAP.md`：我启动后先做什么
